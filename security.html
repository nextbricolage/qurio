Data Security & Privacy Statement

Last updated: 9 November 2026

Qurio Q&A for Confluence ("Qurio", "the app") is a 100% Atlassian Forge app published on the Atlassian Marketplace by nxb labs. This statement explains what data the app processes, how and where it is stored, how it is secured, and how it is retained and deleted. For the full legal privacy terms see the Privacy Policy.

In short: Qurio runs entirely on Atlassian Forge. There is no external backend, no server we operate, and no outbound network calls. All data is stored in Forge Storage inside the customer's own Atlassian Cloud instance and is encrypted at rest by the Atlassian platform. Your content is never transmitted to nxb labs or to any third party outside Atlassian's platform.

1. What data Qurio processes

Qurio only processes data that users create, or that Atlassian provides to the app in order to render its features:

Data Purpose
Questions, answers, tags, votes and "accepted answer" status Core Q&A functionality that users explicitly enter.
Atlassian accountId and public display name of the acting user To attribute questions/answers, compute statistics and expert rankings, and manage moderators and permissions.
Space key and page ID references To scope content to a space and link questions back to their source page.
Group membership (read via the Confluence API, read only) To enforce the optional "who can ask / answer" permission settings and moderator role.
In-app notifications To notify a question's author or followers about new or accepted answers.
Per-macro and instance configuration (e.g. heading, scope, display mode, voting on/off) To remember how each embedded macro and the instance is configured.

Qurio does not collect email addresses, IP addresses, passwords, tokens, payment information, or any special categories of personal data. We store only the Atlassian accountId as the identifier — never passwords, tokens, emails, or usernames — and we never log credentials or secrets. The app uses no cookies, no third-party analytics, and performs no AI/LLM processing of your content.

2. How the data is used

Data is used solely to provide the app's functionality inside your Confluence instance. We do not sell, rent, share, or use your data for advertising, profiling, or any purpose unrelated to operating the app.

3. Where data is stored, residency and access

  • Storage: all application data lives only in Forge Storage within the customer's own Atlassian Cloud environment, encrypted at rest by Atlassian and following Atlassian data residency.
  • No provider access: because the data stays in Forge Storage inside your instance, nxb labs has no routine access to your content. Forge lets developers read application logs for troubleshooting; we only review logs if you contact us with a support request, and we ask you not to include sensitive information in support correspondence.
  • Least-privilege permissions: the app requests only three scopes — storage:app (its own data store), read:confluence-user (resolve a display name for the signed-in viewer) and read:confluence-groups (enforce the who-can-ask/answer and moderator settings). It holds no write scope on Confluence content and reads no page, space, or document bodies.

4. Data retention and deletion

Content remains in Forge Storage until it is deleted through the app or until the app is uninstalled. When you uninstall Qurio, Atlassian removes the app's Forge Storage data according to the Forge platform lifecycle. Within the app you can delete data in two ways:

  • Delete individual posts: the author of a question or answer (and any moderator) can delete it directly. Deleting a question also removes its answers and votes.
  • Delete all my data (right to erasure): from the in-app Help dialog (the "?" button), any user can erase their own personal data. This anonymizes the questions and answers you authored — they are kept, but no longer linked to you, so other people's threads stay readable — and removes the votes you cast, your notifications, and your follows. A moderator can carry out the same erasure on a user's behalf when handling a data-subject request.

See the Privacy Policy for the controller / processor relationship and how to exercise data-subject rights.

5. Our security practices

  • Architecture: 100% Forge. No external backend, no self-hosted servers, no external.fetch / egress permissions. Data lives only in Forge Storage within the customer's Atlassian Cloud instance (encrypted at rest; follows Atlassian data residency).
  • Server-side authorization: every write is validated and authorized server-side in the Forge resolver by a fail-closed role model (author / moderator / configurable group gates); the front end can never grant itself a right.
  • Source control: GitHub with MFA required. Every change is reviewed as a diff and must pass automated security scans (CodeQL, Dependabot, npm audit) before a production deploy, following a documented pre-release checklist.
  • Automated scanning: CodeQL (SAST) on every push/PR and weekly; Dependabot (SCA) for dependency vulnerabilities; npm audit on dependencies.
  • SBOM: a CycloneDX Software Bill of Materials is generated per release for both the Forge resolver and the Custom UI SPA, so the full dependency inventory is auditable.
  • Secure coding: development follows the OWASP Top 10, with server-side input validation (non-empty and length caps) on all user-supplied text.

6. Reporting a vulnerability

If you believe you have found a security vulnerability in Qurio, please report it privately — do not open a public GitHub issue.

  • Email: martinnxb@gmail.com
  • Please include: a description of the issue, steps to reproduce, affected version, and any proof-of-concept details.
  • We acknowledge reports within 2 business days and keep you updated on remediation progress.

Please give us a reasonable window to investigate and fix the issue before any public disclosure. We do not currently operate a paid bug-bounty program, but we credit reporters who responsibly disclose valid issues (with their consent). The latest version published on the Atlassian Marketplace is the supported version and receives security fixes.

7. Incident response

We maintain a documented incident response plan. In the event of a confirmed security incident or critical vulnerability, we notify affected customers and Atlassian in line with Atlassian's Marketplace security policies.
